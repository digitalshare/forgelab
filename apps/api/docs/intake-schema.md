# Intake schema

Delivered by WO-007. Four tables: `challenges`, `agent_runs`,
`evaluation_summaries`, `artifact_metadata`.

**No repository table.** WO-002 already delivered `repository_connections`; a
second one would be two answers to one question.

## Relationships

```
projects
  └── challenges                 (project_id, repository_id?, created_by_user_id?)
        └── agent_runs           (challenge_id, lane 1-3)
              ├── evaluation_summaries   (run_id, unique)
              └── artifact_metadata      (run_id, kind)
```

`repository_id` is `ON DELETE SET NULL`, not `CASCADE` — disconnecting a
repository must not erase the history of what was run against it. Deleting a
challenge does cascade to its runs, summaries, and artifacts: those have no
meaning without it.

`repository_id` is nullable because a sample challenge runs against a curated
fixture rather than a connected repo, and a manual challenge may be drafted
before one is linked.

## Creating a challenge

```python
from forgelab_api.domains.challenges import repository as intake

created = await intake.create_challenge_with_runs(
    session,
    tenant_id=actor.tenant_id,
    project_id=project.id,
    title=..., description=...,
    source_type=ChallengeSource.GITHUB_ISSUE,
    source_ref="1842",
)
# created.challenge, created.runs — three lanes, already numbered
```

A challenge and its three runs are **one fact**. A challenge with two lanes is
not partially created, it is corrupt. The helper wraps both inserts in a
`SAVEPOINT`, so a failure rolls them back as a unit *and* leaves the caller's
outer transaction usable — which is what lets the caller record the failure
afterwards.

Refused before touching the database: anything other than exactly three agent
keys, duplicate keys (three lanes with the same label cannot be told apart in
the UI or in logs), and a GitHub-issue challenge with no `source_ref`.

## Source types

| Source | `source_ref` | Uniqueness |
|---|---|---|
| `github_issue` | issue number, **required** | unique per project |
| `manual` | none | unconstrained |
| `sample` | sample slug | unconstrained |

The uniqueness rule is a **partial** index (`WHERE source_type =
'github_issue'`), so re-importing an issue is refused while manual challenges
may repeat freely. `find_challenge_by_issue` supports idempotent intake for
WO-018.

## Lanes

Three, fixed: `builder-a`, `builder-b`, `specialist` — two independent builders
and one specialist with a different system prompt. The comparison is the
product, so the lanes are not configurable. `UNIQUE (challenge_id, lane)` means
an orchestrator retrying a launch cannot produce a fourth agent.

## Shared lifecycle vocabulary

`challenges.status` and `agent_runs.status` use the same `ChallengeState` and
`RunState` enums the **policy rules** evaluate. Both now live in
`domains/constants.py`; `policy.rules` re-exports them.

Without that, a challenge could be `complete` in the database and something else
to the rule deciding whether a pull request may open.

## ⚠️ Autogenerated migrations try to delete your CHECK constraints

When this migration was autogenerated, Alembic also emitted **eight**
`drop_constraint(..., type_='check')` calls against tables the change did not
touch — `audit_events`, `policy_decisions`, `project_memberships`,
`repository_connections`.

It cannot match a non-native enum CHECK constraint against model metadata, so it
reads every one as an orphan and proposes removing it. Applying that unedited
would have stripped the database-level guard from every enum column in the
schema, silently, while every other test still passed.

**Inspect every autogenerated migration for stray check-constraint drops before
committing it.**

`tests/test_schema_guards.py` now enforces this: it asserts all twelve
enum-backed CHECK constraints exist after migrations *and* that each still
permits every value its Python enum defines. If a migration drops or outdates
one, it fails and names it.

## Placeholders

`evaluation_summaries` and `artifact_metadata` are intentionally thin. The real
evaluation model arrives with WO-038 and scoring with WO-042; these exist so a
run has somewhere to put objective results and artifact references from the
start.

`thresholds_met` is the field the policy service reads for the pull-request
gate. It is **stored, not derived** — the passing bar stays defined in the
evaluation pipeline, not in policy.

`forge_score` is `Numeric(6,2)` rather than a float, so a ranking cannot shift on
a rounding difference between machines.

Artifacts store **metadata only**; anything over ~1 MB lives in object storage
and is referenced by URI with a checksum, so a served artifact can be shown to be
the one that was evaluated.
